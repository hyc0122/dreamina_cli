# 项目优化设计

日期：2026-06-19

## 背景

Dreamina CLI 即梦批量生产工具已经具备独立后端、Vite React 前端、队列 worker、资产管理、大模型设置、打包脚本和 GitHub README。近期更新把项目推到了 GitHub，并把 README 调整为 GitHub 可读的项目入口。

当前需要进入一次项目级治理优化，目标不是一次性大重构，而是让项目后续开发、发布和使用更稳定：每次更新有版本号和更新内容，README 不继续膨胀，代码边界更清楚，用户操作路径更容易理解。

## 优化目标

1. 发布维护可追踪：每次更新必须有版本号、日期和更新内容记录。
2. 文档层级清晰：README 保持入口说明，详细内容沉到专门文档。
3. 代码结构可持续：减少超大文件和重复入口带来的维护成本。
4. 用户体验更稳：启动、队列、模型、弹窗、错误状态都有明确反馈。
5. 发布质量可检查：发布前有固定本地检查流程，避免构建产物和本地运行数据进入版本库。

## 阶段方案

推荐按三个阶段推进，顺序为发布维护、用户体验、代码结构。

### 阶段一：发布维护与文档规范

新增根目录 `CHANGELOG.md`，作为唯一完整更新日志。每次项目更新都新增一条版本记录，包含：

- 版本号
- 发布日期
- 更新摘要
- 新增内容
- 修复内容
- 调整内容
- 已知限制

README 只保留：

- 当前版本
- 更新日志链接
- 项目简介
- 环境要求
- GitHub 拉取方法
- 安装和启动方法
- 基本使用流程
- 关键详细文档链接

详细使用说明继续放在 `docs/使用说明.md`，打包说明放在 `docs/打包版使用说明.md`。README 不承载完整变更历史，也不承载内部发布筛选细节。

版本号采用 `v主版本.次版本.修订号`：

- 主版本：数据结构、启动方式或核心工作流有不兼容变化。
- 次版本：新增页面、模块、重要能力或明显工作流调整。
- 修订号：修复、文案、样式、小范围兼容性调整。

当前项目版本从 `v0.1.0` 开始，后续每次用户确认发布更新时递增版本，并同步：

- `CHANGELOG.md`
- `README.md` 当前版本
- `pyproject.toml`
- `frontend/package.json`

### 阶段二：用户体验稳定化

优先优化用户直接感知的问题。

启动体验：

- 启动页展示后端 API、队列 worker、前端服务状态。
- 服务异常时显示可理解原因和日志入口。
- 本地启动脚本输出访问地址、进程 PID 和数据目录。

队列体验：

- 队列页突出 worker 在线状态、队列开关、在途任务数、最近心跳。
- 阻塞状态显示原因，例如未登录、积分不足、限流、队列满、网络暂时失败。
- 重试和取消操作保留确认提示，避免误操作。

模型体验：

- 大模型页面用状态标签区分“图片已适配”和“视频未完全适配”。
- 资产管理只显示可用于图片生图的模型。
- 分镜工作台和即梦设置只显示可用于视频生成的模型。
- 即梦官方模型和大模型配置模型保持分组展示，避免用户误以为接口能力一致。

弹窗和表单体验：

- 所有大弹窗统一使用不透明 `modal-panel`。
- 参数设置弹窗只保存参数，不提交分镜。
- 批量提交按钮只负责提交，必须选中分镜。
- 表单保存成功、失败、加载中状态都使用统一样式。

### 阶段三：代码结构治理

前端已经拆出 `pages`、`assets`、`workbench`、`llm` 目录，但根目录仍保留多个兼容导出文件。后续建议逐步做以下整理：

- 保留兼容导出一段时间，但新代码只从实现目录导入。
- 对 `JimengSettingsPage.tsx` 继续拆分为登录状态、全局视频参数、队列调度、CLI 能力、返回日志等子组件。
- 对 `jimengApi.ts` 按项目、分镜、资产、队列、设置、LLM 拆分 API 模块，再提供统一导出。
- 对 `assetManagerShared.ts` 中的模型列表、表单转换、提示词拼接继续拆分，让模型配置更容易维护。

后端已经拆出 `api`、`storage`、`providers`、`queue`、`llm`，但仍有几个文件偏大：

- `backend/app/api/settings.py`：拆分为 CLI 设置、模型能力、队列设置、登录动作。
- `backend/app/jimeng_storage.py`：继续变成门面层，具体 SQL 逻辑下沉到 `storage/*`。
- `backend/app/jimeng_cli.py`：拆分 CLI 命令构造、图片模型校验、登录动作解析。
- `backend/app/jimeng_queue.py`：保留队列主流程，错误策略和引用素材构造继续放在子模块。

模型配置建议形成“模型注册表”：

- 前端展示使用同一份结构化模型定义。
- 后端能力返回由结构化模型定义生成。
- CLI 校验从同一份定义派生，减少前端、后端、CLI 三处手工同步。

## 数据流建议

版本发布数据流：

1. 开发者完成更新。
2. 按变更类型确定下一个版本号。
3. 更新 `CHANGELOG.md`。
4. 同步 README 当前版本和包版本文件。
5. 运行本地验证命令。
6. 提交并推送。

模型选择数据流：

1. 大模型设置保存 provider 和 model。
2. 前端通过 `buildLlmModelOptions` 按类型过滤。
3. 资产管理读取 `type=image` 模型。
4. 分镜工作台和即梦设置读取 `type=video` 模型。
5. 后端在实际生成接口中校验 provider、model、enabled 状态。

队列数据流：

1. 分镜提交进入 queue item。
2. worker 按调度设置 claim waiting item。
3. provider 执行提交。
4. item 进入 polling/running 状态。
5. worker 定期轮询结果并写入候选视频。
6. 页面通过队列状态和候选记录展示进度。

## 错误处理建议

- 用户可修复错误：显示明确下一步，例如重新登录、检查 API Key、调整模型、降低并发。
- 临时错误：显示退避重试时间和最近一次错误摘要。
- 配置错误：阻止提交并定位到设置页。
- 代码或未知错误：显示简短摘要，详细信息保留在日志或原始返回中。

## 验证建议

发布维护：

- README 顶部能看到当前版本和更新日志链接。
- `CHANGELOG.md` 最新版本与 `pyproject.toml`、`frontend/package.json` 一致。
- 详细使用说明不被重复复制进 README。

用户体验：

- 前端构建通过：`npm run build`。
- 本地启动脚本能启动 API、worker 和网页。
- 队列页能看到 worker 在线状态和最近心跳。
- 大模型设置页能清楚标出图片与视频适配状态。

代码结构：

- 新增页面或模块不继续堆进现有大文件。
- 新增模型只需在模型注册表维护一次。
- 新增 provider 必须声明支持的生成模式和限制。

## 不在本轮解决的内容

- 不重写整个 UI。
- 不一次性替换所有现有兼容导出文件。
- 不把大模型视频生成标记为已完全可用。
- 不把本地测试体系作为公开使用说明的一部分。
- 不改变当前默认端口、默认数据目录和基本启动方式。

## 验收标准

1. 根目录存在 `CHANGELOG.md`，并包含 `v0.1.0` 起始记录。
2. README 顶部包含当前版本和更新日志链接。
3. README 仍能指导用户完成拉取、安装、启动和基础使用。
4. 版本号在 `CHANGELOG.md`、README、`pyproject.toml`、`frontend/package.json` 中一致。
5. 大模型页面明确展示“大模型接口未完全适配”，且说明图片和视频能力边界。
6. 分镜工作台参数设置和批量提交职责清晰。
7. 前端构建通过。

## 自审结果

- 内容完整性检查：没有待补内容、临时标记或空白章节。
- 一致性检查：阶段顺序与推荐路线一致，版本记录规则与 README 瘦身目标一致。
- 范围检查：本设计聚焦项目治理、体验稳定和结构优化，不包含大规模重写。
- 歧义检查：版本同步文件、CHANGELOG 字段、README 保留内容和非目标范围均已明确。
