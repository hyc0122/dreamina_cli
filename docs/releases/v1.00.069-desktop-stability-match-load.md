# v1.00.069 桌面端掉线诊断修复

更新时间：2026-07-06 11:26:59 +08:00

## 背景

对方 Win10 电脑再次出现程序自动掉线后，新增的诊断日志已经能看到明确堆栈，不再只是“主程序没了”的现象。

本次日志里主要暴露两类问题：

1. 首次访问接口时，多个请求同时初始化 `JimengStore`，SQLite schema 迁移并发执行，导致重复添加同名字段。
2. 批量匹配资产时，即使用户只提交少量选中分镜，后端仍会先全量读取当前项目全部分镜并构造 Pydantic 对象，大项目下会造成明显卡顿和崩溃风险。

## 关键日志

第一类异常：

```text
sqlite3.OperationalError: duplicate column name: default_duration
backend/app/api/projects.py -> context.get_store -> JimengStore.__init__ -> init_schema -> _ensure_columns
```

第二类异常集中在资产匹配链路：

```text
backend/app/storage/shots.py shot_from_row
backend/app/storage/shots.py list_shots
backend/app/api/shots.py _target_shots
backend/app/api/shots.py match_assets
```

这说明用户一次性全选后虽然前端和后端已经做了每 5 条分批，但 `_target_shots()` 每批仍然调用 `list_shots(project_id)` 全量加载项目分镜。

## 修改内容

### 1. 后端 store 初始化加锁

`backend/app/api/context.py`

- 新增 `_store_lock`。
- `get_store()` 改为双重检查锁，保证同一进程里只初始化一个 `JimengStore`。
- 测试替换 store 的方法也进入同一个锁，避免测试和运行逻辑不一致。

### 2. SQLite 字段迁移改为幂等

`backend/app/jimeng_storage.py`

- `_ensure_columns()` 捕获 `sqlite3.OperationalError`。
- 如果错误是 `duplicate column name`，说明另一个并发初始化已经完成添加，直接视为成功。
- 其他 SQLite 错误继续抛出，避免吞掉真实数据库问题。

### 3. 选中分镜按 ID 精准读取

`backend/app/storage/shots.py`

- 新增 `list_shots_by_ids()`。
- 只查询用户本次选中的分镜 ID。
- 保持传入 ID 顺序，并校验分镜必须属于当前项目。

`backend/app/jimeng_storage.py`

- 新增 `JimengStore.list_shots_by_ids()` 对外委托方法。

`backend/app/api/shots.py`

- `_target_shots()` 在 `shot_ids` 存在时不再全量 `list_shots()`。
- 改为调用 `list_shots_by_ids()`。
- 未传 `shot_ids` 时仍保持全项目匹配逻辑。

### 4. 保留每 5 条分批

资产匹配仍保留前后端每 5 条分批策略：

- 前端避免一次请求塞入过多分镜。
- 后端避免单个请求内一次处理过多绑定。
- 本次进一步修复每批内部仍全量读取的问题。

## 验证

新增和覆盖测试：

- `tests/test_jimeng_store_concurrency.py`
  - 并发调用 `get_store()` 时只初始化一个 store。
  - 并发 schema 迁移遇到重复加列时不再抛错。
- `tests/test_jimeng_match_batching.py`
  - 选中分镜按 5 条分批。
  - `_target_shots()` 对选中分镜走按 ID 查询，不再全量读取项目分镜。

验证命令：

```powershell

```

结果：

```text
4 passed
```
