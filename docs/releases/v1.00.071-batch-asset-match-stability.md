# v1.00.071 批量资产匹配稳定性修复

更新时间：2026-07-25 21:31:53 +08:00

## 问题表现

- 少量分镜可以正常匹配，数百条分镜全选后执行批量匹配时，桌面程序可能直接退出或显示掉线。
- 前端原来每 5 条分镜发送一次请求，350 条分镜会连续产生 70 次后端请求。
- 后端虽然存在分批逻辑，但进入匹配接口时仍先构造全部目标分镜；每条绑定还会分别打开 SQLite 连接。

## 根因

对桌面故障日志中的原生异常调用栈进行复核后，确认崩溃发生在 Python 垃圾回收阶段。大量匹配请求和未主动关闭的 SQLite 连接在短时间内集中回收，叠加全部分镜对象的重复构造，最终导致打包程序出现原生异常并退出。

这不是提示词太长导致的，也不是单个角色或场景匹配规则导致的。核心问题是批量操作被拆成过多 HTTP 请求，同时数据库写入粒度过细。

## 修改内容

1. 前端批量匹配只发送一次请求，提交全部选中的分镜 ID。
2. 后端按每 5 条分镜执行真实分批：每批只读取当前 5 条分镜和对应绑定。
3. 自动匹配绑定改为单批事务批量删除、批量插入，不再为每条绑定重复打开数据库连接。
4. 匹配热点路径中的 SQLite 连接全部在 `finally` 中主动关闭，不依赖垃圾回收。
5. 接口直接返回所有目标分镜的完整绑定和高亮状态，前端不再额外查询绑定。
6. 分镜 ID 会先去重，避免重复选择造成重复计算和重复绑定。

## 兼容性

- 保留手动绑定，只清理并重建自动匹配绑定。
- 仍按完整资产名称和既有角色、场景、道具规则匹配。
- 用户仍可一次全选全部分镜；“每 5 条”现在由后端内部稳定执行，不需要浏览器连续发起多次请求。
